# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this is

**GitLab Radar** — a single-file [SwiftBar](https://swiftbar.app) menu bar plugin
(macOS) that surfaces GitLab events that otherwise only reach you by email:
broken pipelines, (re-)review requests, and new comments on your MRs. It polls
the GitLab REST API directly — no server, no webhooks. Works with gitlab.com and
self-hosted instances.

Menu bar shows: `🦊 ❌1 👀2 💬1` (dim `🦊` when all quiet).

## Layout

| File                  | Purpose                                                        |
|-----------------------|---------------------------------------------------------------|
| `gitlab-radar.3m.sh`  | **The whole plugin.** All logic lives here. The `.3m.` in the name is the SwiftBar refresh interval (every 3 min). |
| `install.sh`          | Host-side installer/uninstaller — writes config, stores the token in the macOS Keychain, copies the plugin into SwiftBar's plugin folder, stamps the installed version. |
| `bin/gitlab-radar.js` | Thin Node wrapper so `npx github:triffer/gitlab-radar install` works. Maps `install`/`uninstall`/`version` onto `install.sh` — no logic of its own. |
| `README.md`           | User-facing docs (features, config table, how it works).      |
| `package.json`, `.releaserc.json`, `commitlint.config.js`, `.github/workflows/` | Release plumbing — see **Releases** below. |

## Runtime facts

- **Language:** Bash, targeting the stock macOS **bash 3.2** — no associative
  arrays, no `${var,,}`. Keep changes 3.2-compatible.
- **Dependencies:** `bash`, `jq`, `curl` (and `security`/`open`/`afplay` from macOS).
- **Config:** `~/.config/gitlab-radar/config` (plain bash, sourced by the plugin).
- **Token:** macOS Keychain, service `gitlab-radar` (or `GITLAB_TOKEN` in config).
- **State/cache:** `~/.cache/gitlab-radar/` (read-markers, project cache, token
  info, sound snapshot, `update.json` = newest release seen + when we last asked).
- **Version stamp:** `~/.config/gitlab-radar/installed.sh`, generated by
  `install.sh` and sourced by the plugin *after* the config, so a stray
  assignment in that user-edited file can't shadow it.
- **Menu actions** (mark read, mark to-do done, rotate token, check/copy update)
  are the script **re-invoking itself** with a flag — see the `case "${1:-}"`
  block near the top (`--seen`, `--seen-all`, `--open-seen`, `--todo-done`,
  `--rotate`, `--check-update`, `--copy-update`).

## How the plugin runs

SwiftBar executes `gitlab-radar.3m.sh` every 3 minutes. Each run:
1. Prints the menu-bar title line (first line of stdout).
2. Prints `---`, then dropdown rows in SwiftBar's format
   (`text | key=value key=value`), grouped into sections.

Data comes from a few API calls per refresh: `merge_requests` (yours + as
reviewer), `todos`, plus per-MR `notes`/`approvals`/`pipelines`. See the
"How it works" table in `README.md` for the exact endpoints.

## Releases

Versions are cut by **semantic-release** from Conventional Commits on `main` —
never edit `package.json`'s version (it says `0.0.0-development` in the repo)
and never write `CHANGELOG.md` by hand; both are release-time artifacts.

- Commit messages must be conventional (`feat:`, `fix:`, `docs:`, `chore:` …);
  `.github/workflows/ci.yml` runs commitlint over every commit in a PR and
  `bash -n` over the shell scripts. Dependabot's own commits are exempt
  (`ignores` in `commitlint.config.js`): it writes a `Bump x and y` header and
  compare links longer than the 100-column body limit on one line.
- `.github/workflows/release.yml` runs on push to `main`: tag, changelog,
  `package.json` bump, GitHub Release. Nothing is published to npm
  (`npmPublish: false`) — the **git tag is the release artifact**, because
  users install via `npx github:triffer/gitlab-radar#v<version> install`.
- The plugin's last dropdown row shows the installed version (from the stamp, or
  a sibling `package.json` when run from a checkout — otherwise `vdev`) and, once
  per `UPDATE_CHECK_HOURS`, whether a newer release exists. The check never runs
  inline: the render reads `update.json` and spawns a **detached** `curl` whose
  result the *next* refresh shows, and the cache is stamped *before* fetching so
  an offline machine costs one attempt per window, not one every three minutes.
- Nothing in the menu ever installs an upgrade — it copies the command
  (`update_command()`) to the clipboard. The installer is interactive and a menu
  bar plugin is no place for a prompt. Keep it that way.
- Only a plain `MAJOR.MINOR.PATCH` counts as a version (`version_sane`), so
  network input and hand-edited stamps can't smuggle markup into a menu row or a
  URL. An unrecognised version renders `vdev` and never claims an update.
- Adding a config key means two places in `install.sh`: the heredoc for a fresh
  config, and a `grep -q '^KEY='` append for existing ones.

## Working here

- This is macOS/SwiftBar tooling — it can't be run meaningfully inside the Linux
  sandbox (no menu bar, no Keychain). Validate changes by reading, `bash -n`
  syntax-checking, and `jq` snippet testing rather than a full run.
- Preserve the SwiftBar output format: the first stdout line is the title; `|`
  separates the label from parameters, so user text is passed through
  `sanitize()`. `--` prefixes create submenu rows.
- Match the existing style: heavy inline comments explaining *why*, `jq -r @sh`
  + `eval` to unpack JSON into shell vars, defensive `|| default` fallbacks.
